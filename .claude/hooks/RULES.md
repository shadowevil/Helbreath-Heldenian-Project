# Project hook rules

Contents: Layout - D1: linked doc over 10 KB - N1: d-030 (not hookable) - A1: d-035 archive before replace (log-only, partly checkable) - B1: d-038 client code stays off backend APIs (log-only, partly checkable).

## Layout

- `doc_size_guard.py` - thin PostToolUse entry point for `Write|Edit|MultiEdit`; `--self-test` runs every rule's cases plus an end-to-end run (never touches the real log).
- `hooklib/paths.py` - project root (`CLAUDE_PROJECT_DIR`, else the event `cwd`) and anchored relative-path matching. `hooklib/output.py` - ASCII text, locked log append with a 2 MB cap and one rotation, the PostToolUse context JSON.
- `rules/<action>/<id>_<name>.py` - one module per rule: its check, message and `SELF_TEST` cases. `rules/__init__.py` collects them.
- `replay_d1.py` - read-only replay over the project's transcripts. `doc_size_exempt.txt` - D1's documented exceptions.
- Hits go to `.claude/hooks/log/doc_size_hits.jsonl` (gitignored). Everything is stdlib only, fails open and prints ASCII; nothing blocks.

## D1: linked doc over 10 KB

- **Rule** (user, 2026-11-23, HH-0027 / d-026): "the goal is to keep documentation files under 10kb when linked to the CLAUDE.md - if it gets bigger than that it needs to be audited ...". Recorded in `.claude/docs/documentation.md`. The global docs standard sect. 1 has the same ~10 KB "assess" trigger, so the rule is generic: nothing in the code names this project.
- **Class:** hookable as a flag (PostToolUse cannot deny, and size alone never decides). Id `D1`, module `rules/write/d1_doc_size.py`.
- **Covers:** root `CLAUDE.md` (d-016) and every `.claude/docs/**/*.md`, anchored at the root (copies under `.claude/scratch/` are not docs). The limit is 10,240 bytes. `documentation.md`'s own PowerShell check uses `-gt 10000`, so the two disagree by 240 bytes.
- **Logged per hit:** `size` (from disk), `prev_size` (from `tool_response.originalFile`, CRLF-corrected; else the Edit string delta; unknown for `replace_all`), `crossed`, `step_crossed`, `exempt`, `assessed` (an italic `*Assessed` or bold `**Assessed` line in the first 60 lines), `would_flag`, `flagged`, `bucket`.
- **Flags** (with `--flag` only) when a doc that is not exempt either just crossed 10 KB, is over with no assessment line, or is assessed and just grew past another 2 KB step. Once per session, path and 2 KB bucket.
- **Modes:** log-only by default. `--flag` shows the message to the agent. `CLAUDE_DOC_SIZE_GUARD=log` is a kill switch. `--hits-path=` or `CLAUDE_DOC_SIZE_GUARD_HITS_PATH` redirects the rows.
- **Known gaps:**
  - Writes made through Bash or PowerShell (Mode 2 scripts, `git mv`) are not seen.
  - **Exempt docs never flag or re-flag, however large they grow.** `tickets.md` is the one exempt doc; growth past a 2 KB step is logged (`step_crossed`) but never shown. Removing a line from `doc_size_exempt.txt` is the only way to bring a doc back under the flags.
  - The step re-flag is a staged proposal, not a user ruling. It exists because of the decisions.md finding below.
- **Measured 2026-11-23** (one `replay_d1.py` run: 100 transcripts, 1,259 file writes, 114 to covered docs):
  - **Coverage.** 65 of the 114 were judged: 41 directly from their results, 24 rebuilt by chaining each doc's last full Read or Write. The other 49 are unknown: Edits whose result has a null `originalFile` and no chain. Most are CLAUDE.md (38), which is now 9,921 B. Back-chaining its Edit deltas from that size puts its peak at about 10,067 B: no hit, but 173 B under the limit (estimated). The live hook reads the size from disk and has no such gap.
  - **Hits.** 11, all on `.claude/docs/decisions.md`. One crossing (9,700 -> 11,271), then 10 edits on to 15,101 bytes. The chain's last size matches the 15,101 bytes measured on disk before the split.
  - **Flags.** Without the step rule there is 1 would-flag. The doc's "kept whole, one file" assessment line was already there at 9,700 B, under the limit, and it silenced the other 10. With the step rule there are 3 (11,271, 12,326 and 14,608). The doc was then audited and split (HH-0025, done; now 5,292 B plus six sidecars).
  - **False positives.** 0 of 11 hand-checked: every hit is a doc linked from CLAUDE.md line 19 and really over 10 KB.
  - **Boundary cases.** None: no hit or near miss falls within one byte per line of the limit.
  - **The `assessed` signal.** 13 of the 36 covered docs carry an `*Assessed` line now. So "over with no assessment line" is a real branch, not one that almost never fires.
  - **Over the limit now:** `.claude/docs/tickets.md` (37,899 B, exempt) and `.claude/docs/ccontrols-reference/core.md` (11,042 B). No transcript write touched core.md, so D1 will log it on its next Write or Edit.
- **Cost** (measured): 70-74 ms median per call under `python -I -S`, max 139 ms. A bare interpreter start alone takes 38 ms.

## N1: d-030 (not hookable)

- **Rule** (user, 2026-11-24): "Finish all of hte tickets - if something needs my eye then it should go into user review". Recorded in `.claude/docs/ticket-workflow.md` "Status".
- **Class:** not hookable. Id `N1`; nothing is built.
- **Why:** it governs when a session stops and what it parks. "Finished everything the team can" and "needs the user's eye" are judgments about the work, not properties of a tool call. A Stop hook cannot tell a legitimate stop (waiting on a user decision put in chat) from an early one. The ticket moves go through `author.py` and `tickets.py`, which hold no "should this go to user_review" signal.
- **Possible future check (not built):** a Stop hook that lists tickets still `in_progress` while no agent is running. It would report a symptom of the rule, not the rule itself, and it needs the ticket store's schema, which the ticket system's maintainer owns.

## A1: archive before replace (log-only)

- **Rule** (user, 2026-11-25, d-035 in `.claude/docs/decisions/ui-look.md`): "We should also be replacing lower quality versions if we have a hd counterpart"; "Archiving the old versions". Where an HD asset exists the game draws it at every scale and the low-res version is archived byte-identical under `working/archive/`, never deleted.
- **Class:** partly checkable. Id `A1`, module `rules/execute/a1_archive_before_replace.py`, entry `archive_guard.py`. No existing rule covers it (global W-rules guard where writes land and how deletes are spelled, not whether the old bytes were kept).
- **Checkable:** a Bash, PowerShell, Write, Edit or MultiEdit call that deletes, moves away or overwrites a tracked art file (png, jpg, bmp, gif, webp, tga, psd) under `staged/client/sprites/` whose last committed bytes (git HEAD blob) match no file under `working/archive/`. Matching is by content hash anywhere in the archive, so the layout stays free. Verbs parsed: `rm`, `del`, `Remove-Item`, `git rm`, `mv`, `git mv`, `cp`, `Copy-Item`, `>`; directories and a last-segment glob expand through `git ls-tree`. A `cp` from `working/classic_ui/hd/` is logged `src_hd` (the d-035 replacement case).
- **Not checkable:** whether an HD counterpart exists and is wired in (that half of d-035 is a judgment about the art), and anything done inside a script (python, build tools, `--pathspec-from-file`, `$var` paths).
- **Why PostToolUse, log-only:** at that point the old bytes are gone from disk, so HEAD is the reference; a file never committed has nothing to archive and is ignored. To enforce, move the same `judge()` to PreToolUse and hash the file's current bytes instead of HEAD's; do not do that before the replay below is accepted.
- **Why not a build-time or git hook:** `working/` is gitignored, so a pre-commit hook cannot see the archive, and a build never sees a deletion. A pre-commit check of "deleted art blobs have a matching file under `working/archive/`" is possible on the one machine that has `working/`, but it fires after the damage and not for uncommitted churn. The tool-call hook is the earliest point.
- **Layout:** `archive_guard.py` is the thin entry (121 lines); `hooklib/gitstate.py` holds `blob_sha`, the HEAD and archive look-ups (capped at 300 files; a hit row carries `truncated: true` when the cap cut the list); `hooklib/a1_selftest.py` holds the end-to-end self-test.
- **Modes:** log-only by default to `.claude/hooks/log/archive_hits.jsonl`; `--flag` shows the agent one message per session and file set; `CLAUDE_ARCHIVE_GUARD=log` is the kill switch; `--hits-path=` redirects. Fails open.
- **Measured 2026-11-25** (staged copy; `--self-test` 68/68 incl. end-to-end cases in a throwaway git repo that it removes afterwards; `replay_a1.py` and `.claude/scratch/hooks/d035/history_check.py`):
  - **Replay, static layer.** 1,730 transcript tool calls mention `sprites`; 20 are examined (11 Bash deletes, 4 PowerShell deletes, 10 `cp` from `working/classic_ui/hd/` overwrites, 1 other overwrite; 26 path entries) in 5 transcripts; 5 of the 20 (3 distinct commands) also name `working/archive` (they delete files archived earlier). The git/disk layer cannot be replayed (the old state is gone).
  - **Parse accuracy.** All 20 hand-checked: each really deletes or overwrites a sprite. 0 false positives. Misses: 213 sprite-mentioning shell calls with a verb word extracted nothing; sampled, nearly all are reads, greps, `git commit` text or script-internal; one real miss is `git rm --pathspec-from-file`.
  - **Hash match on real history** (measured): 94 art files deleted or modified under `staged/client/sprites/` over git history; 44 old blobs are in the archive, 50 are not. The 50 all predate d-035 (47 map-kit minimaps in one commit, 3 kit-art rewrites), so a live hit there would have been a true "unarchived" but not a d-035 breach; the retirements done under d-035's practice (game_dialogs, front-end screens, panel kit) all matched.
  - **Cost, two measurements.** (1) Author, `d035/cost.py`: wall time of one `python -I -S archive_guard.py` subprocess per event (Python startup included), 7 runs each, on a quiet machine: 94 ms median when the call names no sprite path (the common case), 115 ms for one tracked file, 133 ms for a directory; max 140 ms. D1 measured the same way is 70-74 ms. (2) Reviewer: about 360 ms wall for a no-op event, also with startup, on a busier machine. Expect 100-400 ms per Bash/PowerShell call depending on load; this is the main cost to weigh before install.
- **Known gaps:** PostToolUse sees the command, not what a script did; two rewrites of one file before a commit compare against the same HEAD blob; generated kits rewritten by their build script are invisible, and a manual rewrite of one is a likely false positive.

## B1: client code stays off backend APIs (log-only)

- **Rule** (user, 2026-11-25, d-038 in `.claude/docs/decisions/graphics-protocol.md`): "it should be a graphics protocol addition not implemented for just SFML - all graphic frameworks that use the graphics protocol should implement their own way to match the spec". Display and window capabilities live in the engine-neutral protocol (`sources/dependencies/shared/render/`: `renderer.h`, `window.h`) and each backend (`sources/sfml_engine/`) implements them; `sources/client/` calls only the interface.
- **Class:** partly checkable. Id `B1`, module `rules/write/b1_backend_isolation.py`, entry `backend_guard.py`. No existing rule covers it.
- **Checkable:** a Write, Edit or MultiEdit of a C++ file (cpp, cc, c, h, hpp, inl) under `sources/client/` whose ADDED text introduces a backend token: an include whose path contains `sfml` (`<SFML/..>`, `"sfml_window.h"`, `"sfml_engine/.."`), `sf::`, a type `SFML<Upper>..` (SFMLWindow) or an identifier `sfml_..`. Comments and string literals are ignored (the client has comments naming SFMLWindow and `sf::String`); a token already in the replaced text does not count; `SFML_ENGINE` style build macros are not matched. A Write's baseline is the result's `originalFile`.
- **Not checkable:** whether a capability is specified in the protocol at all, whether a new interface method is engine-neutral, and whether a backend implements it (judgment about the design); backend calls reached through a type alias or a `void*` native handle (`get_back_buffer_native`); writes made through Bash/PowerShell or scripts. Only `sources/client/` is covered; `sources/ccontrols/` and the protocol headers themselves are not (shared/render has `sf::` in four comments today).
- **Build-time check:** a better enforcement point than the hook for the include half. A CMake or grep step that fails when any file under `sources/client/` matches `#include.*[Ss][Ff][Mm][Ll]` or `\bsf::` (code, not comments) catches every writer, not only tool calls, and is exact. The hook is the early, cheap nudge during editing. Not built here (outside this task's scope: it needs a build-script change by the build owner).
- **Why PostToolUse, log-only:** it cannot deny, and the rule is new; to enforce, move the same `classify()` to PreToolUse (it already works from the call's own text, no disk state) once the replay below is accepted.
- **Modes:** log-only by default to `.claude/hooks/log/backend_hits.jsonl`; `--flag` shows the agent one message per session and path; `CLAUDE_BACKEND_GUARD=log` is the kill switch; `--hits-path=` redirects. Fails open, ASCII only.
- **Measured 2026-11-25** (staged copy; `backend_guard.py --self-test` 60/60 incl. 50 rule cases and 10 end-to-end; the other two entries still pass, 114/114 and 118/118. Also matched: `sf ::`, `sf/*c*/::`, `using namespace sf`, `namespace x = sf;`; C++ raw strings (R"d(...)d", u8R) are skipped; `replay_b1.py`, `replay_b1_mentions.py`):
  - **Today's tree.** `sources/client` has 311 C++ files and 0 backend-API hits (measured by running `classify()` over every file with an empty baseline). The one `sf::`/`<SFML/` grep line is the CMake `GIT_REPOSITORY` URL; the other `SFML` mentions are 5 comments naming SFMLWindow, build files and `Client.vcxproj` (not covered).
  - **Replay.** 208 transcripts, 9,057 Write/Edit/MultiEdit calls, 2,279 on covered client files: 0 hits. The 9 covered calls that mention `sfml` or `sf::` at all are all comments (hand-checked, all 9): correctly silent, so 0 false positives. There are no true positives in history either, so the must-fire side is proven by the self-test cases only (measured gap).
  - **Cost** (measured): 83 ms wall for a no-op event under `python -I -S` including interpreter start.
- **Known gaps:** a fragment edit that starts inside a block comment can be misread; `old_string` that contains the violation but is not an exact textual match of the new one counts as new (rare, errs toward a hit).
